# Node.js Backend

Навчальна CRM API на Express.js 5, TypeScript, Prisma, PostgreSQL, Redis, MongoDB і WebSocket.

## Вимоги

- Node.js 22+
- npm
- Docker (або локально: PostgreSQL 17+, Redis 7+, MongoDB 7+)

## Локальний запуск

Два способи, і вони не виключають один одного. Команди стека запускаються з
кореня репозиторію — там, де лежать `package.json` і `compose.yaml`.

**Усе в контейнерах** — нічого не треба ставити, крім Docker і Node.js:

```bash
npm run setup
npm start
```

Докладніше — у README кореня репозиторію.

**Застосунок на машині, сховища в контейнерах** — описано нижче. Дає дебагер,
читабельні логи й перезапуск без контейнера посередині.

### 1. Налаштувати оточення

```bash
npm run setup
```

Команда створює кореневий `.env` і `.env` цього модуля з шаблонів, з
новими секретами й паролями сховищ. Нічого правити не треба. Якщо файли вже є,
команда їх не чіпає.

Файли поділені за тим, кому належать значення:

- **кореневий `.env`** — спільне для стека й застосунку: `APP_ENV`, порти
  (`API_PORT`, `POSTGRES_PORT`, `REDIS_PORT`, `MONGO_PORT`) і облікові дані
  сховищ (`POSTGRES_*`, `MONGO_*`);
- **`.env` цього модуля** — лише бекенду: JWT-секрети, пароль наповнення, логи,
  CORS, ліміти, кеш, інтеграції.

Застосунок, наповнення бази й команди Prisma читають обидва файли однаково.
Пріоритет — від найвищого: змінні, з якими запущено процес, далі `.env` цього
модуля, далі кореневий. Файла може й не бути: у контейнері все приходить
змінними середовища.

Адреси сховищ окремо прописувати не треба. Якщо `DATABASE_URL`, `REDIS_URL` чи
`MONGODB_URL` не задано, застосунок збирає їх із частин кореневого `.env` на
`127.0.0.1` — не `localhost`: на Windows ім'я спершу резолвиться в IPv6, і кожне
з'єднання зі сховищем, що слухає лише IPv4, чекає на це дві секунди. Явно
заданий URL завжди має пріоритет — так його й перевизначають на сервері чи в CI.

Значення в цих файлах мають обмеження, і перевіряють їх у різні моменти:

| Змінна               | Вимога                        | Хто перевіряє            |
| -------------------- | ----------------------------- | ------------------------ |
| `JWT_ACCESS_SECRET`  | щонайменше 32 символи         | застосунок на старті     |
| `JWT_REFRESH_SECRET` | щонайменше 32 символи         | застосунок на старті     |
| `SEED_USER_PASSWORD` | від 12 знаків, не `change-me` | сценарій наповнення бази |

Паролі сховищ (`POSTGRES_PASSWORD`, `MONGO_PASSWORD`) лежать лише в кореневому
`.env`: з ним сховища створюються, з нього ж застосунок збирає адреси, тож
розійтися їм нема де.

### 2. Підняти сховища

```bash
npm run start:infra
```

PostgreSQL, Redis і MongoDB доступні на `127.0.0.1` з портами `POSTGRES_PORT`,
`REDIS_PORT` і `MONGO_PORT` з кореневого `.env` (за замовчуванням `5432`, `6379`
і `27017`) — з тих самих значень застосунок збирає адреси. Команда
повертається, коли всі три здорові. API в контейнері при цьому не запускається,
тож порт `8000` вільний.

### 3. Поставити залежності

```bash
cd backend
npm ci
```

У виводі має бути рядок `Generated Prisma Client`. Клієнт бази не лежить у
репозиторії: його щоразу генерують зі `prisma/schema.prisma`, і `npm ci` робить
це сам. Після будь-якої зміни схеми крок повторюють окремо:

```bash
npm run prisma:generate
```

### 4. Застосувати міграції й наповнити базу

```bash
npm run db:migrate:deploy
npm run db:seed
```

Обидві команди читають обидва `.env` так само, як застосунок. Повторний запуск
нічого не ламає: застосовані міграції пропускаються, а наповнення лише оновлює
наявні записи.

### 5. Запустити

```bash
npm run dev
```

Готовність видно за рядком `HTTP server listening` у логах. Перевірити ззовні:

```bash
curl http://localhost:8000/api/health/ready
```

Відповідь `{"status":"ready", ...}` містить перелік залежностей, і кожна має
бути `up`. Якщо котрась `down`, вона названа поіменно — це і є місце, куди
дивитися.

Сервіс доступний на `http://localhost:8000`; усі його маршрути лежать під `/api`:

- `GET /api/health/live` — процес живий
- `GET /api/health/startup` — застосунок завершив старт
- `GET /api/health/ready` — залежності доступні
- `GET /api/health/info` — назва, версія, середовище, uptime
- `GET /api/docs` — Swagger UI
- `GET /api/openapi.json` — OpenAPI документ
- `GET /api/metrics` — метрики Prometheus (лише якщо задано `METRICS_TOKEN`)
- `/api/v1/...` — маршрути API
- `WS /api/v1/realtime` — канал подій реального часу

Порт береться з `PORT`, а без нього — зі спільного `API_PORT` кореневого `.env`.

### Зупинити

Сам застосунок — `Ctrl+C` у його терміналі. Сховища — з кореня репозиторію:

```bash
npm stop         # дані лишаються
npm run clean    # разом із базами
```

### Повернути базу до початкового стану

База локальна й нічия, тому найпростіший шлях — знести її разом із томом і
підняти заново:

```bash
npm run clean
npm run start:infra
```

Після цього повтори крок 4. У повному стеку (`npm start`) міграції й наповнення
відпрацьовують самі.

### Якщо не запускається

**`@prisma/client did not initialize yet`.** Клієнт бази не згенерований. Так
буває, коли залежності ставили з `--ignore-scripts`. Лікується
`npm run prisma:generate`.

**`Invalid environment configuration`.** Застосунок перелічує поля, які не
пройшли перевірку, і вимогу до кожного. Найчастіше це `JWT_ACCESS_SECRET` або
`JWT_REFRESH_SECRET`, замінені на щось коротше за 32 символи. Якщо в переліку
`DATABASE_URL` чи `MONGODB_URL`, адресу не вдалося зібрати: у кореневому `.env`
бракує `POSTGRES_USER`, `POSTGRES_PASSWORD` чи `POSTGRES_DB`, або `MONGO_DB`.

**`ECONNREFUSED` на `:5432`, `:6379` або `:27017`.** Сховища не підняті або вже
зупинені. Перевір `npm run ps` у корені репозиторію.

**Пароль не підходить до бази.** Найчастіше в `.env` цього модуля лишився
власний `DATABASE_URL` чи `MONGODB_URL` зі старим паролем: явна адреса має
пріоритет над зібраною. Прибери рядок — адреса збереться з кореневого `.env`.

**`port is already allocated`.** Порт зайнятий іншою програмою або другим
стеком. Node- і Python-стеки використовують однакові порти, тому одночасно
працює лише один: зупини попередній.

**Застосунок стартував, але відповідає не він.** Ознака — `uptimeSeconds` у
`GET /api/health/info` набагато більший за вік твого процесу, а зміни в коді на
відповідь не впливають. Це контейнер `api` повного стека на тому самому
`:8000`: два процеси на одному порту на Windows стартують без помилки, а запити
дістаються лише одному. Зупини стек (`npm stop`) і підніми тільки сховища
(`npm run start:infra`) або візьми інший `PORT` у `.env` цього модуля.

**Контейнер висить у стані `Created`.** Docker не може змонтувати робочу теку.
Перевір, що диск, на якому лежить проєкт, відкритий у налаштуваннях Docker
Desktop (Settings → Resources → File sharing).

**Контейнер перезапускається, у логах `sh: tsx: not found`.** Це не зламана
збірка, а **застарілий том із залежностями**. У режимі розробки залежності API
лежать в іменованому томі, і Docker наповнює такий том з образу **лише коли той
порожній**: новий образ до старого тому не доїде, скільки не перезбирай.

Лікується перестворенням тому, бази при цьому не чіпаються:

```bash
npm stop
docker volume rm practice-crm-nodejs_api_node_modules
npm start
```

Перший запуск після цього довгий — залежності ставляться наново.

## Змінні середовища

Звідки застосунок бере значення й у якому порядку — у кроці 1 вище. `NODE_ENV`
окремо не задають: застосунок виставляє його з `APP_ENV`, щоб бібліотеки бачили
те саме середовище.

**Кореневий `.env`** — спільне для стека й застосунку:

| Змінна              | Призначення                                              |
| ------------------- | -------------------------------------------------------- |
| `APP_ENV`           | Середовище: `development`, `test` або `production`       |
| `API_PORT`          | Порт API, якщо не задано `PORT`; за замовчуванням `8000` |
| `POSTGRES_PORT`     | Порт PostgreSQL, за замовчуванням `5432`                 |
| `REDIS_PORT`        | Порт Redis, за замовчуванням `6379`                      |
| `MONGO_PORT`        | Порт MongoDB, за замовчуванням `27017`                   |
| `POSTGRES_DB`       | Назва основної бази                                      |
| `POSTGRES_USER`     | Користувач PostgreSQL                                    |
| `POSTGRES_PASSWORD` | Пароль PostgreSQL                                        |
| `MONGO_DB`          | Назва бази подій                                         |
| `MONGO_USER`        | Користувач MongoDB                                       |
| `MONGO_PASSWORD`    | Пароль MongoDB                                           |

**Адреси сховищ** — збираються з частин вище, якщо не задані явно. Явне значення
завжди має пріоритет:

| Змінна                                      | Як збирається                                                                                                                                |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`                              | `postgresql://POSTGRES_USER:POSTGRES_PASSWORD@POSTGRES_HOST:POSTGRES_PORT/POSTGRES_DB?schema=public`                                         |
| `REDIS_URL`                                 | `redis://REDIS_HOST:REDIS_PORT`                                                                                                              |
| `MONGODB_URL`                               | `mongodb://MONGO_USER:MONGO_PASSWORD@MONGO_HOST:MONGO_PORT/MONGO_DB?authSource=admin`; без користувача й пароля — без них і без `authSource` |
| `POSTGRES_HOST`, `REDIS_HOST`, `MONGO_HOST` | Хости сховищ, за замовчуванням `127.0.0.1`; у контейнері — імена сервісів                                                                    |

**`.env` цього модуля** — лише бекенду:

| Змінна                         | Призначення                                                          |
| ------------------------------ | -------------------------------------------------------------------- |
| `HOST`                         | Адреса прослуховування HTTP-сервера                                  |
| `PORT`                         | Порт HTTP-сервера; перекриває `API_PORT`                             |
| `LOG_LEVEL`                    | Рівень логування Pino                                                |
| `CORS_ORIGINS`                 | Дозволені origins через кому                                         |
| `JSON_BODY_LIMIT`              | Максимальний розмір JSON body                                        |
| `JWT_ACCESS_SECRET`            | Секрет access token, щонайменше 32 символи                           |
| `JWT_REFRESH_SECRET`           | Секрет refresh token, щонайменше 32 символи                          |
| `SEED_USER_PASSWORD`           | Пароль синтетичних користувачів seed, від 12 знаків                  |
| `SEED_ALLOW_PRODUCTION`        | `true` дозволяє наповнювати базу при `APP_ENV=production`            |
| `REDIS_KEY_PREFIX`             | Префікс ключів кешу                                                  |
| `CACHE_TTL_SECONDS`            | Час життя кешованих значень                                          |
| `RATE_LIMIT_WINDOW_SECONDS`    | Вікно обмеження частоти запитів                                      |
| `RATE_LIMIT_MAX_REQUESTS`      | Ліміт запитів у вікні для загальних маршрутів                        |
| `AUTH_RATE_LIMIT_MAX_REQUESTS` | Ліміт запитів у вікні для маршрутів автентифікації                   |
| `EVENT_LOG_RETENTION_DAYS`     | Скільки днів зберігаються доменні події                              |
| `WS_PATH`                      | Шлях WebSocket-каналу                                                |
| `METRICS_TOKEN`                | Токен доступу до `/api/metrics`, від 16 символів; без нього вимкнено |
| `SHUTDOWN_GRACE_PERIOD_MS`     | Скільки чекати на завершення активних запитів                        |
| `SHUTDOWN_TIMEOUT_MS`          | Верхня межа всієї процедури зупинки                                  |
| `SHUTDOWN_DRAIN_DELAY_MS`      | Пауза між відмовою в готовності та закриттям слухача                 |

## Команди

```bash
npm run dev        # запуск у режимі розробки
npm run build      # production build
npm start          # запуск зібраного застосунку
npm run lint       # ESLint
npm run format     # перевірка Prettier
npm run typecheck  # перевірка TypeScript
npm test                    # unit та module-level тести
npm run test:integration    # integration тести (потребують npm run start:infra)
npm run ci                  # статичні перевірки, unit-тести та build
npm run prisma:generate     # перегенерувати клієнт бази після зміни схеми
npm run prisma:validate     # перевірити саму схему
```

`npm test` проходить без піднятих сховищ: наскрізні набори в нього не входять і
названі окремим рядком у кінці прогону. Запускає їх `npm run test:integration`
з цієї теки — після `npm run start:infra` у корені репозиторію. Тестові бази
раннер виводить із того самого `.env` і створює сам; подробиці — у
`tests/integration/README.md`.

## Демонстраційний набір даних

Поверх базового seed можна завантажити великий набір за дванадцять місяців —
сотні контактів і угод, близько тисячі замовлень, рухи товару й аудит:

```bash
npm run db:seed:demo
```

У повному стеку те саме робить `npm run db:seed:demo` з кореня репозиторію — він
запускає команду в контейнері.

Це **окрема команда й окремі дані**. Базовий seed вона не чіпає: видаляє лише
ті рядки, які сама ж і записала минулого разу, тож запускати її можна скільки
завгодно разів. Рядки беруться з `prisma/demo-data/` — готового набору файлів у
репозиторії.

Порядок має значення: `npm run db:seed` спершу, `npm run db:seed:demo` після —
ролі демонстраційних облікових записів шукаються за назвою, а не створюються.

## Скрипти обслуговування

```bash
sh scripts/db-reset.sh      # скинути, змігрувати та засідити базу, до якої веде .env
```

Скрипт відмовляється працювати при `APP_ENV=production` і питає підтвердження;
у неінтерактивній оболонці потрібен `--yes`. Підняти, зупинити чи зібрати стек —
команди й bash-скрипти кореня репозиторію.

## Docker

Образ збирається з `Dockerfile` цього модуля в кілька стадій:

| Стадія         | Що в ній                                            | Хто використовує                        |
| -------------- | --------------------------------------------------- | --------------------------------------- |
| `dependencies` | усі залежності й згенерований клієнт бази           | режим розробки: код монтується зверху   |
| `build`        | зібраний застосунок разом з інструментами           | сервіс `migrate`: міграції й наповнення |
| `runtime`      | лише зібраний код і production-залежності, без root | `npm run prod:start` і сервер           |

Стек описано в `compose.yaml` кореня репозиторію; режим розробки накладається
поверх нього з `compose.override.yaml`.
