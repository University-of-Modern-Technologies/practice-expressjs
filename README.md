# Навчальна CRM — запуск

Система складається з веб-клієнта (`frontend/`), HTTP API на Node.js (`backend/`)
і трьох сховищ: PostgreSQL, Redis і MongoDB. Усе разом піднімається однією
командою через Docker Compose.

## Вимоги

- Docker Desktop (або Docker Engine) з Docker Compose v2.
- Node.js 22 — для команд `npm run …` і для запуску частин системи на машині.

Без Node.js стек теж запускається, через bash-скрипти або напряму через Docker
Compose — див. «Без обгорток» нижче.

## Швидкий старт

```bash
npm run setup   # створює файли .env з новими секретами й перевіряє порти
npm start       # збирає й піднімає стек, чекає, поки все стане здоровим
```

Відкрий **http://localhost:8080**. Перший запуск займає кілька хвилин через
збірку образів, наступні — секунди. Команди працюють у PowerShell, cmd, bash і
zsh.

## Команди

| Команда | Що робить |
|---|---|
| `npm run setup` | створює `.env` і `backend/.env`; секрети генерує нові; показує зайняті порти |
| `npm start` | увесь стек у Docker у режимі розробки; API перезапускається при збереженні файла |
| `npm stop` | зупинити стек; дані лишаються |
| `npm run build` | зібрати production-образи |
| `npm run prod:start` | стек із production-образів — так, як він працював би на сервері |
| `npm run prod:stop` | зупинити production-стек; дані лишаються |
| `npm test` | юніт-тести бекенда й веб-клієнта, на машині |
| `npm run check` | усе, що перевіряє CI: формат, лінт, типи, юніт-тести, збірка |
| `npm run check:backend` | те саме лише для бекенда; `check:web` — лише для клієнта |
| `npm run test:integration` | інтеграційні тести бекенда проти сховищ `start:infra` |
| `npm run start:api` | лише API і його сховища, без клієнта й проксі |
| `npm run start:infra` | лише PostgreSQL, Redis і MongoDB — для API, запущеного на машині |
| `npm run dev` | API на машині на порту 8000, проти `start:infra`; не стартує, якщо порт зайнятий |
| `npm run dev:web` | веб-клієнт на машині на порту 3000, з гарячим перезавантаженням |
| `npm run logs` | логи всіх сервісів; `npm run logs -- api` — одного |
| `npm run ps` | стан кожного сервісу |
| `npm run clean` | зупинити стек і видалити бази (питає підтвердження) |
| `npm run tools` | Portainer: контейнери, їхні логи й стан |
| `npm run db:migrate` | застосувати міграції й базове наповнення |
| `npm run db:seed:demo` | завантажити великий демонстраційний набір даних |
| `npm run install:all` | поставити залежності бекенда й клієнта для роботи на машині |

## Два режими стека

| | `npm start` (розробка) | `npm run prod:start` (як на сервері) |
|---|---|---|
| Файли compose | `compose.yaml` + `compose.override.yaml` | лише `compose.yaml` |
| API | код монтується з `backend/`, перезапуск при збереженні | зібраний образ, без вихідного коду |
| Веб-клієнт | production-збірка | production-збірка |
| Середовище застосунку | `development` | `production` |

`compose.yaml` описує систему так, як вона працює на сервері.
`compose.override.yaml` додає поверх неї режим розробки, і `docker compose`
підхоплює його сам, коли файл лежить поруч.

Збірка й запуск production-стека — окремі кроки: `build` збирає образи один
раз, `prod:start` запускає вже зібрані й добирає лише відсутні.

Веб-клієнт в обох режимах зібраний — так стек займає сотні мегабайт пам'яті, а
не гігабайти. Щоб правити клієнт із гарячим перезавантаженням, запусти його на
машині: `npm run dev:web` (http://localhost:3000). Запити до `/api` він пересилає
на `http://127.0.0.1:8000` — байдуже, хто там слухає: контейнер `api`
(`npm run start:api` — API і сховища без клієнта й проксі) чи API на машині
(`npm run start:infra` і `npm run dev`).

Production-стек — навчальний стенд, тому базове наповнення з обліковими
записами нижче працює й у ньому. Дозволяє це `SEED_ALLOW_PRODUCTION=true` у
`backend/.env`; без цього рядка наповнення в production відмовляється
запускатися.

## Тести й перевірки

| Що | Команда | Що потрібно |
|---|---|---|
| юніт-тести | `npm test` | залежності на машині: `npm run install:all` |
| усе, що перевіряє CI | `npm run check` | те саме |
| інтеграційні тести бекенда | `npm run start:infra`, потім `npm run test:integration` | запущені сховища |

`check` запускає рівно ті скрипти, що й CI, тож зелений `check` на машині —
це зелений pipeline.

Інтеграційні тести працюють з окремими базами `<назва>_test` у тих самих
контейнерах, тож робочих даних не чіпають. Тестова база створюється сама.
Окремого файла оточення для тестів немає: адреси й паролі беруться з тих самих
`.env`. Контейнери тести не запускають — якщо сховища не відповідають, команда
падає й називає, яке саме і як його підняти.

**Хук перед комітом.** `setup` ставить git-хук (husky і lint-staged): перед кожним
комітом він форматує й лінтить лише ті файли, що йдуть у коміт. Тести хук не
запускає — для них `check`. Виправлене форматування хук сам додає в коміт; помилку лінтера, яку не
виправити автоматично, він показує й зупиняє коміт. Разово обійти хук — `git commit --no-verify`;
CI однаково перевірить те саме.

## Облікові записи

Пароль для всіх трьох — значення `SEED_USER_PASSWORD` з `backend/.env`; `npm start`
друкує його наприкінці.

| Пошта | Роль |
|---|---|
| `admin@crm-training.example` | повний доступ |
| `manager@crm-training.example` | робота з даними |
| `viewer@crm-training.example` | лише читання |

## Адреси

| Адреса | Що це |
|---|---|
| http://localhost:8080 | застосунок — єдина потрібна адреса |
| http://localhost:8080/api/docs | Swagger UI: контракт API |
| http://localhost:8080/api/health/ready | стан застосунку та його залежностей |
| http://localhost:9000 | Portainer, після `npm run tools`: логін `admin`, пароль у `.portainer-password` |

Порти окремих сервісів теж відкриті — щоб підключитися клієнтом БД або
звернутися до API повз проксі. Сховища слухають лише `127.0.0.1`.

API завжди на 8000, веб-клієнт завжди на 3000 — у Docker і на машині, з
будь-яким бекендом. Тому клієнт знаходить API без жодного налаштування, а
на одному порту одночасно працює щось одне.

| Змінна в `.env` | Типово | Сервіс |
|---|---|---|
| `HTTP_PORT` | 8080 | застосунок через nginx |
| `API_PORT` | 8000 | API напряму |
| `WEB_PORT` | 3000 | веб-клієнт напряму |
| `POSTGRES_PORT` | 5432 | PostgreSQL |
| `REDIS_PORT` | 6379 | Redis |
| `MONGO_PORT` | 27017 | MongoDB |
| `PORTAINER_PORT` | 9000 | Portainer |

## Склад системи

| Сервіс | Роль |
|---|---|
| `nginx` | єдиний вхід: `/api/…` і WebSocket — до API, решта — до клієнта |
| `web` | веб-клієнт |
| `api` | HTTP API і канал реального часу |
| `migrate` | застосовує міграції та наповнює базу, після чого завершується |
| `postgres` | основне сховище: користувачі, контакти, угоди, товари, замовлення |
| `redis` | кеш і облік частоти запитів |
| `mongo` | журнал доменних подій |
| `portainer` | керування контейнерами й перегляд логів; лише з `npm run tools` |

Схема бази накатується автоматично: `migrate` відпрацьовує до старту `api`, а
`api` не запускається, поки той не завершиться успішно. Повторний запуск нічого
не ламає — застосовані міграції пропускаються, а наповнення лише оновлює наявні
записи.

## Структура

```
compose.yaml            система так, як вона працює на сервері
compose.override.yaml   режим розробки поверх неї
.env.example            спільне оточення: середовище, порти, назви й паролі баз
package.json            команди стека й хук перед комітом (husky, lint-staged)
lint-staged.config.mjs  що хук перевіряє і чим
.husky/                 сам хук
scripts/                реалізація команд, bash-дублери, раннер хука
etc/nginx/              конфігурація проксі
backend/                HTTP API — див. backend/README.md
frontend/               веб-клієнт — див. frontend/README.md
```

## Файли `.env` — який для чого

| Файл | Що в ньому | Хто читає |
|---|---|---|
| `.env` | спільне: `APP_ENV`, порти, назви й паролі баз | Docker Compose; API на машині |
| `backend/.env` | лише бекенд: секрети, пароль наповнення, ліміти, інтеграції | контейнери `api` і `migrate`; API на машині |

`setup` створює обидва з шаблонів `*.env.example`. Веб-клієнт власного файла
оточення не має: адреса API в ньому відносна, `/api/...`.

API читає спершу змінні процесу, потім `backend/.env`, потім кореневий
`.env`; перше знайдене значення перемагає. Адреси сховищ (`DATABASE_URL`,
`REDIS_URL`, `MONGODB_URL`) у файлах не пишуться: API збирає їх на старті з
частин — `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`,
`POSTGRES_PASSWORD`, `POSTGRES_DB`, і так само для Redis та MongoDB. Хост
типово `127.0.0.1`, а в Docker `compose.yaml` ставить імена сервісів. Тож
API на машині й API в контейнері працюють з тією самою базою, і пароль лежить
в одному місці. Явно задана адреса перемагає зібрану — так API направляють на
інший сервер.

Docker Compose бере з кореневого `.env` лише значення для підстановки в
`compose.yaml` і цілком його контейнерам не роздає.

## Без обгорток

Команди вище — тонкий шар над Docker Compose. Те саме bash-скриптами (у Windows —
з Git Bash):

```bash
./scripts/start.sh        # режим розробки
./scripts/stop.sh
./scripts/build.sh        # production-образи
./scripts/prod-start.sh
./scripts/prod-stop.sh
./scripts/test.sh
```

І напряму:

```bash
docker compose up -d --build --wait                 # розробка: override підхоплюється сам
docker compose -f compose.yaml up -d --build --wait # як на сервері
docker compose logs -f api
docker compose down
```

Без `setup` достатньо скопіювати `.env.example` у `.env` і
`backend/.env.example` у `backend/.env`: шаблони містять робочі локальні
значення. `start.sh` і `build.sh` роблять це самі, якщо файлів ще немає.

## Якщо не запускається

**Порт зайнятий.** `npm run setup` показує зайняті порти заздалегідь; під час
запуску це помилка `port is already allocated`. Постав інше значення в `.env`
(`HTTP_PORT`, `POSTGRES_PORT` тощо) і запусти знову. На Windows порт може бути
зарезервований системою без жодної програми на ньому — це видно з
`netsh interface ipv4 show excludedportrange protocol=tcp`.

**`dev` пише, що порт 8000 зайнятий.** Найчастіше його тримає контейнер `api`
цього ж стека. Два процеси на одному порту на Windows стартують без помилки й
ділять запити між собою, тому `dev` перевіряє порт заздалегідь. Зупини стек
(`npm stop`) і підніми лише сховища (`npm run start:infra`).

**Змінив `.env`, а нічого не змінилося.** Значення потрапляють у контейнер при
його створенні. Потрібно `npm stop`, потім `npm start`; самого `restart` замало.

**Додав залежність, а її не видно.** У режимі розробки модулі API живуть в
окремому томі, який переживає звичайний перезапуск. Після зміни
`backend/package.json` зупини стек і видали том — бази при цьому не чіпаються:

```bash
npm stop
docker volume rm practice-crm-nodejs_api_node_modules
npm start
```

**Змінив файл, а нічого не сталося.** Зміни відстежуються опитуванням раз на
пів секунди, тож дай пару секунд. Якщо не допомогло — `npm run logs -- api`:
там видно, чи застосунок узагалі перезапустився. Зміни веб-клієнта в контейнері
не підхоплюються взагалі — для них `npm run dev:web`.

**Логи виглядають як суцільний JSON.** Так і має бути: у контейнері немає
інструмента розфарбовування, він потрібен лише в розробці. Читабельні логи —
у запуску на машині через `npm run dev`.

**Що зі стеком насправді.** `npm run ps` показує стан кожного сервісу, а
`/api/health/ready` — чи бачить API свої залежності. Якщо якесь сховище лежить,
воно буде названо там поіменно.

**MongoDB падає одразу після старту на старому комп'ютері.** MongoDB 5 і новіші
потребують процесора з підтримкою AVX. На машинах без неї контейнер `mongo`
завершується без зрозумілого повідомлення.
